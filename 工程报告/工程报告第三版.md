## 1. 演进动因（v2 实机跑出来的四个坑）

| 坑 | 现象 | 根因 |
|---|---|---|
| 重嵌风暴 | 当日 md 每次追加触发整文件 delete+reindex，600+ 块重嵌半小时 | v2 把原文全文都嵌了，原文是最高频变化的文件（5.4 增量阈值只止血未治本） |
| KV 502 抖动 | 本地 embedding（llama.cpp）大请求偶发 502 | 批量太大，单请求 KV 吃满 |
| chroma 文件锁 | Windows 下 chroma 目录搬不动、删不掉 | PersistentClient 的 HNSW mmap 句柄长期持有 |
| 数据臃肿 | 17MB chroma + 55MB 索引，一天 1MB 原文 | 对话块与 md 原文同一数据存两遍（ingest 链路冗余） |

核心结论（chroma 冗余账）：向量库的独家能力只剩**语义匹配**（忘了关键词时）；相关性排序、增量维护、规模扩展三条优势在文件层可以用"日记当索引 + 时间偏置"逼近七八成。于是拍板：**日记放 db，其他走 grep**。

## 2. 按会话隔离存储（space.py `SpaceManager`）

### 2.1 目录结构

```
memory/                                  # workspace_path，原 workspace/，2026-08-16 改名
├── MEMORY.md                            # （可选）根级共享 .md，列入 inject_files 注入所有会话
└── <UMO 冒号换下划线>/                   # 每个白名单会话一个空间
    ├── MEMORY.md                        # 该会话的小本子（注入 + 5 个 memory_* 工具）
    ├── memory/
    │   ├── YYYY-MM-DD.md                # 每日原文（纯 grep，不建索引）
    │   └── diary/YYYY-MM-DD.md          # 每日日记（唯一向量化对象）
    └── chroma/                          # 该会话独立向量库（只嵌 diary 块）
```

- `is_active(session_id)`：白名单片段匹配（白名单项可填完整 UMO 或能唯一区分的片段；留空=全启用）
- per-session 缓存：vdb / searcher / notebook / 注入文本（`_inject_cache` 按会话 key）
- 未命中白名单的会话：钩子全静默（不捕获、不注入、不建空间）

### 2.2 路由点（main.py 全量改造）

- 注入：`_build_inject` 按会话取自己空间的 MEMORY.md；缓存失效点=该空间 MEMORY.md 的 watcher 事件
- watcher：`_space_dir_of(path)` 按路径第一层目录名路由回会话；原文变化→不建索引（仅日志），diary 变化→按增量阈值重建，MEMORY.md→刷注入缓存
- index_state：key 加空间前缀 `<UMO>/memory/diary/xxx.md`
- daily_hook / digest_worker：`daily_file_for` / `diary_file_for` 按会话路由

### 2.3 存量迁移（2026-08-16 完成）

1. 旧 `workspace/{MEMORY.md, memory/}` + 旧 flat `chroma/` 整体迁入主会话空间

## 3. 双层检索（memory_search 改造）

### 3.1 分工

| 层 | 对象 | 手段 | 解决什么 |
|---|---|---|---|
| 向量层 | diary/*.md（一天几块） | chroma 语义检索 | 忘了关键词、要脉络 |
| grep 层 | memory/*.md 原文 + MEMORY.md | 逐行关键词现扫 | 关键词明确、要精确定位 |

`source` 参数语义：**all**（默认，两层都查）/ **diary**（只向量）/ **raw**（只 grep）。
`time_range` 参数：`Nm/Nh/Nd/Nw`（如 7d、24h、30m、2w），按文件名日期截；留空不限。

### 3.2 grep 层规格（纯 Python 零依赖）

- 多词 query = 同一行须包含全部词（AND）；单词 = 子串匹配
- 新文件优先（按文件名倒序），**最多 20 文件、每文件最多 4 命中、总计最多 8 条**
- 每条命中 = 匹配行 + 前后各 1 行上下文，标 `[grep | 文件名:行号]`
- 小本子（MEMORY.md）也在候选里：虽已整篇注入，留作 /mem test 靶子与未来"只注入最近 N 条"的退路，成本≈0
- 性能实测：940KB 原文 20 次查询 0.14s

### 3.3 删除的链路

- `ingest_conversations` / `ConversationIngestor` / `_on_conv_done` 整条线**删除**（原 v2 的"降级保留"进一步清退）：原文 md 已含全部对话，双存纯冗余
- `_reindex_all`（/mem rebuild）只索引 diary/
- watcher 对原文文件不再建索引，只做日志

## 6. 日记层备选方案（2026-08-16 08:18 讨论留档）

现方案 = "压缩摘要（AstrBot 上下文压缩的免费产物，钩子已捕获）+ 当天尾部原文 → 人设 LLM 写日记"，已贴成本下限。备选：

1. **索引层跳板（small-to-big）**：只嵌"首句+关键词"机器索引块，命中后按块号回原文捞整段。省 23:30 LLM 调用；代价是无叙事。
2. **懒总结（on-demand）**：召回失败/用户问某天才现场总结并缓存；代价是首查慢、无每日节奏。可作现方案的叠加优化。
3. **事实抽取（mem0 式）**：抽原子事实进事实库，日记整个消失；换范式，维护复杂，暂不跳。
4. **原文直接全嵌**：v2 方案，重嵌风暴已证伪。

结论：现方案保持；嫌结算 LLM 贵了先叠方案 2；1、3 记着。

## 8. 捕获降噪 + 摘要检查点（2026-08-16 08:35 追加）

### 8.1 背景

实测量 2026-08-16.md（875KB，全天代码日）：user+assistant 真对话仅 6.9%，〔think〕25.6%、工具结果 63.3%、tool_calls 3.3%——噪音 92.2%，全量请求体落盘对 grep 是噪音湖。同日确认压缩为滚动摘要（单槽重写），一天 30 次压缩（128K 窗口）意味着只存最新摘要会把早间细节传话磨没。

### 8.2 捕获降噪（源头过滤）

- `_norm_content(think_cap)`：结构化 think 片段按 `capture_think_chars` 截留，0=整段跳过（默认）
- `render_msg(tool_cap)`：工具结果按 `capture_tool_chars` 截留，0=整条跳过（默认）；空内容消息不渲染（防 `assistant: ` 孤儿行）
- tool_calls 维持只留工具名一行（面包屑），JSON 参数不存
- 正文 think 标签清洗 `_clean_think_tags`：模型抽风把 `
` 写进正文时，完整配对（含内容）删除、孤立标签只剥壳
- 实测预期：875KB 代码日 → 约 70KB，grep 命中基本全是对话

### 8.3 摘要检查点（summary_states）

- store 新增 `summary_states: [{ts, text}]`：每次捕获到新滚动摘要追加一版（去重），不丢中间态
- 结算喂入：`_render_states` 拼"检查点"（各时刻摘要快照，带 HH:MM 标），超 `digest_state_budget`（默认 24000 token）时保最早一条 + 自最新往前取
- 传话损耗从 N 跳收敛到 1 跳（每个检查点离当时原文一跳）
- 日记失败兜底改用最新检查点；成功后 `summary_states=[]` 与 summary 一起焚
- 兼容：老条目只有 summary 时包成单检查点

### 8.4 新增配置

| key | 默认 | 说明 |
|---|---|---|
| `capture_think_chars` | 0 | 〔think〕 截留字符数，0=跳过 |
| `capture_tool_chars` | 0 | 工具结果截留字符数，0=跳过 |
| `digest_state_budget` | 24000 | 检查点输入预算 (token)，超出采样 |

### 12.5 M6-9 冷启动延迟加载（新增，01:43 全量重启实锤）

**现象**：01:43:32 全量重启，embedder.load() 连续 6 次 `Provider openai_embedding was not found`（10s 间隔），白卡 50s 后 early-return，watcher/reindex 全跳过。

**根因**：core_lifecycle.py 启动顺序 `plugin_manager.reload()` 先于 `provider_manager.initialize()`，插件 initialize 时 provider 尚未实例化。M6-7 的 6×10s 重试全撞空窗。

**修法**：embedder.load() + 初始重建索引从 initialize 主路径挪进后台延迟任务 `asyncio.create_task(self._deferred_embedder_load())`；memory_search 加 `asyncio.shield` + 65s 超时等待延迟任务完成；terminate 取消未完成任务。共 5 处 file_edit，py_compile 过。效果：事件循环一让出 provider 已灌满立即成功，不阻塞主初始化。

**验证**：02:02:19.990 延迟加载开始 → 02:02:20.158 就绪（168ms），索引 0 重建 2 跳过，无 50s 卡顿无重试。

**附带发现**：50s 启动阻塞大概率拖慢 webchat HTTP 上线（「超时一直被 ban」的根因之一）。
