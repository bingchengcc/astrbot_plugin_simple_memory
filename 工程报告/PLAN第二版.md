## 一、核心概念：三层记忆

| 层 | 位置 | 内容 | 写入方式 |
|---|---|---|---|
| 顶层 小本子 | workspace/MEMORY.md | 共同记忆：agent 判断值得长记、经用户确认的事实 | agent 问 → 用户点头 → memory_append 工具 |
| 中层 摘要+原文 | 插件 data 目录 JSON（摘要）+ memory/日期.md（原文按轮次 diff 追加） | 各会话最新压缩摘要 / 逐字对话原文 | on_llm_request 单钩子双动作（每条用户消息触发一次，按轮次粒度）：摘要 upsert 存储、原文 diff 落 md |
| 下层 日记 | memory/日期.md | 当天摘要的日记化整理 | 23:30 worker 从存储组装，人设模型写，摘要用完即焚 |

## 二、小本子（顶层）

- 触发规则：插件注入的指令块告诉 agent——遇到值得长期记的稳定事实（习惯、规则、坑、偏好），在回复末尾自然带出「要记入我的小本子吗」
- 模板灵魂在末尾引导语，前半句是正常聊天收尾；名字跟人设走（小本子/小黑本）
- 条目格式：`序号. [日期时间] 内容`，序号写入时递增、**不可变**（删除留洞不重排，避免模型引用错位）
- 工具（插件内实现、操作 workspace/MEMORY.md，不走文件工具白名单，单锁串行写）：
  - `memory_read()`：读全文（带序号）
  - `memory_append(content)`：追加，自动分配序号+日期前缀
  - `memory_edit(序号, 新内容)`：按序号精准替换单条（日常编辑主路径，翻车半径一行）
  - `memory_delete(序号)`：删除单条
  - `memory_write(content)`：整体替换（大扫除逃生门，平时不碰）
- 讨论编辑流程：memory_read 调现状 → 聊天里说改哪条怎么改 → 用户点头 → memory_edit/delete 落盘
- 防翻车：任意写操作前旧版存 MEMORY.md.bak（兜底）；memory_write 后新内容 < 旧 50% 记 warning
- 写完 watcher 2 秒内刷新注入，下一条消息即新版
- 提问门槛：只问稳定事实，不问即时状态（心情、今天吃了啥）
- MEMORY.md 只走注入不进向量库（已改），确认一条就永久在场

## 三、上下文摘要 + 原文记录（中层，单钩子双动作）

- 核心：**一个 on_llm_request 钩子，per 会话，两个动作**
  - 动作① 盯 contexts 中的 user 消息「Our previous history conversation summary: 」前缀（**M1 已确认：摘要是 user 消息不是塞 system**），摘要变更 → upsert 进存储（插件目录 JSON：会话 ID → {最新摘要, 最后压缩时刻, 上次上下文快照}）；滚动累积特性=新摘要含旧内容，每会话只留最新版
  - 动作② diff 当前请求体 vs 该会话上次快照：**消失的老内容=刚被压缩走的原文段**，直接追加落当日 md；**新增消息=增量原文**，也追加落当日 md（纯追加不重写）
  - 效果：逐字原文按轮次进 md（本轮内容下一轮开始才落盘，一轮延迟，对日记无影响），比 chroma 异步入库更快；压缩触发=上下文>82% 窗口，保留最近 15% 原文（tail）
- 23:30 worker：拿存储里最后一次上下文快照补落当天最后一段尾巴 → 用存储摘要（+补尾摘要，超 ~2000 token 才补）写日记追加到同文件 → 清存储条目
- 轻日子：当天原文总量小、无压缩 → 钩子照常逐条追加原文，零 LLM 调用
- **退场清单**：chroma astrbot 源、TTL 清扫、对话异步入库链路全部退场；watcher 本来就索引 md，memory_search 变单水源且带逐字，小本子/日记/原文同一套文件体系
- 多会话按会话各算各的；会话水位线保证跨天长会话不重不漏
- 代价（已接受）：重日子文件大（几百 KB~几 MB，永久无 TTL）；watcher 一天多次增量索引（纯追加可控）
- 兜底路径输入控制：代码块占位（``` → [代码约 N 行]）、长度截断
- 成本：最坏情况每活跃会话每天一发便宜摘要调用（夜间）

## 四、日记（下层）

- 每日 worker，默认 23:30
- 触发条件：当天存在摘要类内容（压缩摘要或补尾摘要）才写日记；纯原文记录的轻日子默认不写（可配置）
- 输入：当天摘要区内容（不是原始聊天，输入小一个数量级）
- 模型：人设绑定的 LLM，人设卡塞 system，「以角色风格把以下内容总结为日记」
- 日记死规矩：只记决定/结论/踩的坑/偏好，不抄代码，改动只记文件名+改了什么
- 跳板（摘要）用完即焚：摘要不进文件，worker 组装时只落日记；日记失败/空返回则摘要原文直接充当当天记录落盘
- 当天文件最终形态（从上到下）：原文段（按时间序，钩子实时追加）→ 补落的最后尾巴 → 日记本体（重日子）；日记失败则存储摘要当记录；不写覆盖时间头行（过渡日窗口只在 worker 日志留痕）
- 窗口日志三用途：过渡日怪窗口唯一留痕 / 补跑超窗（>24h）溯源 / 日记质量核对原料区间
- digest_time 变更容忍：机制=水位线→当前时刻，切换只产生一个过渡日文件（懒版，接受过渡期），次日起稳定新标准，旧文件不迁移
- 天数判定备注：无独立边界逻辑——事件按原始对话真实时间戳落桶，总结按水位线→当前收集，文件名=运行日期；配置仅 digest_time 一个旋钮

## 五、注入扩展（on_llm_request）

- 现状指针块（每请求现算，digest 开启时拼）：

  - 「原文已在 memory/日期.md（可直接读/grep），日记尚未生成」

## 六、前端（_conf_schema.json 新增）

- `digest_enabled`：自动日记开关（默认开）
- `notebook_name`：小本子的名字（默认「小本子」），进指令块模板
- `digest_time`：日记时间（默认 23:30），**天数边界跟着它走**：一天=上次总结时刻→本次总结时刻，凌晨内容归下一天文件，保证"先摘要原文、后日记"的文件顺序
- `raw_ttl_days`（可选）：原文保留天数，默认 0=永久；到期=worker 重写老文件留日记删原文段（与日记同文件，故为小重写非删除）

## 十、编码时待确认

- ~~**压缩结构验证（唯一要真查源码的问题）**~~ **M1 已确认（2026-08-16 读源码）**：
  - 压缩器：默认 TruncateByTurnsCompressor（砍最老轮次无摘要）；配 `llm_compress_provider` 才走 LLMSummaryCompressor（本部署=摘要模式）
  - 压缩后结构 = `[首部 system…] + user(摘要前缀+全文) + assistant(固定 ACK 句) + 最近轮次原文`（15% token 预算按轮保留，最新轮必留；压缩后写回 run_context 持久化）
  - 压缩时机：每次 LLM 调用前 process()，on_llm_request（provider 层）看到的就是压缩后列表；触发=usage>82%
  - **结论：新旧列表非简单前缀关系 → diff 定稿为锚点对齐算法**（见工程报告 4.3）；砍轮次模式与压缩超窗减半截断同被该算法覆盖
  - **M2 实测修正（2026-08-16）**：on_llm_request 触发点 = internal.py `call_event_hook(OnLLMRequestEvent)`，**每条用户消息只触发一次**（build_main_agent 之后、runner 工具循环之前）；工具循环内多次 LLM 调用是 runner 直接取 `run_context.messages` 打 provider，不再触发钩子。故双动作粒度 = **每用户轮次**：轮次开始时看到的是上一轮完整持久化历史（含工具消息），本轮自己的工具调用过程要等下一轮才开始才落盘；工具循环中发生的压缩已持久化，下一轮 diff 按 vanished/inserted 捕获。钩子异常被 call_event_hook 捕获不阻断主流程，仅 `event.stop()` 才掐请求（两个钩子均返回 None，安全）
  - M2 验证（2026-08-16）：session_store / daily_md / daily_hook 落地，27 项单测全过（含压缩三形态/幂等/基线保护/跨日分文件）；实机：重启后首轮建 191 条基线（只记不落盘），memory/ 暂空，第二轮触发 diff 落盘验证
- request 结构化拆桶后再 diff：system / 历史 / user / assistant / 插件注入分开，只对 conversation 消息做结构化 diff（指针块日期变化进不了 diff 视野）
- diff 锚点：消息条数+首尾指纹（不全文哈希，省内存快）
- 压缩块的获取：on_llm_request 里 diff 压缩标记的可行性，AstrBot 压缩输出的具体格式/标记
- 插件内 provider 直连调用 API（日记任务用，不经过 agent 循环）
- 指令块由插件 on_llm_request 拼接（不动人设指令），随 digest_enabled/notebook_name 动态生成
- 首请求基线规则：新会话/新周期第一次快照只记录不追加，防止整段上下文灌进新文件
- 锁：同进程 asyncio 一把锁，hook 追加与 worker 追加共用（同生命周期），每次 append 锁内完成，防 原文/日记/原文 交错
- worker 消费存储后只清"已消费摘要"；长会话的快照与水位线跨天保留
- 钩子的"当前文件日期"口径（digest_time+上次运行时刻）与 worker 一致，凌晨消息归下一天文件
