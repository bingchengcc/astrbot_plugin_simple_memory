## 3. 数据结构

### 3.1 会话存储 `data/session_store.json`（持久化，重启不丢）

```json
{
  "webchat_xxx": {
    "summary": "最新压缩摘要全文",
    "last_compress_ts": 1787123456,
    "watermark_ts": 1787081580,
    "snapshot": {
      "count": 42,
      "head_fp": "sha1:abc…",
      "tail_fp": "sha1:def…",
      "messages": [{"role": "user", "text": "…"}, …]
    },
    "summary_consumed": false
  }
}
```

- `snapshot`：上一次请求的 conversation 消息（role+text 精简结构），diff 基准
- `watermark_ts`：上次 digest 完成时刻，窗口 = watermark → now
- `summary_consumed`：worker 清"已消费摘要"标记；长会话的 snapshot/watermark 跨天保留
- 写入时机：每次 on_llm_request 原子替换（单进程 asyncio 锁内）

### 3.2 当日文件 `workspace/memory/YYYY-MM-DD.md` 区块格式

```markdown
## [14:32][webchat_xxx]
user: 原文…
assistant: 原文…

## [15:01][webchat_xxx]
user: （刚被压缩走的原文段）…

## [23:30][tail:webchat_xxx]
（worker 补落的最后尾巴）

# 日记 2026-08-16
（人设模型输出；日记失败时此区块改放摘要原文并标注 [摘要代记]）
```

- 文件日期口径：`current_cycle_date(now, digest_time, last_run_ts)` —— 一天 = 上次总结时刻 → 本次总结时刻，凌晨消息归下一天文件，钩子与 worker 共用同一函数
- 写入：全部走 `daily_md.append(date, block)`，内部持 `self._daily_lock`（asyncio，与 worker 同一把）

## 4. 钩子实现（`daily_hook.py`，挂 `_inject` 同链路）

### 4.1 请求拆桶（**M1 已确认字段**）

`on_llm_request` 拿到 `req: ProviderRequest`（`core/provider/entities.py` L91），实际字段：

```
req.contexts: list[dict]   # OpenAI 格式消息列表（含 system/user/assistant/tool），diff 对象
req.system_prompt: str     # 系统提示词（含本插件注入块）
req.session_id: str        # 存储 key（比 event.unified_msg_origin 稳）
req.conversation.token_usage  # 可信 token 用量
```

只对 `req.contexts` 做结构化 diff，system_prompt 变化（指针块日期、注入块）不进 diff 视野。
钩子位于 provider 层，每次 LLM 调用都触发（工具循环内多次），看到的一定是压缩处理后的列表（runner 在调用前 process 并写回 run_context.messages）。

### 4.2 动作①：摘要捕获

- 在 system 中找固定前缀「Our previous history conversation summary: 」后的全文
- 与 store 中该会话旧摘要比对，变化 → 更新 `summary` / `last_compress_ts`

### 4.3 动作②：锚点对齐 diff → 原文落 md（M1 定稿算法）

M1 结论：压缩后列表 = `[system…] + 摘要 user 消息 + 固定 ACK + 最近轮次原文`，与旧快照**非简单前缀关系**，故算法分两步：

1. **先试纯前缀增长**：new 以 old 为前缀（工具循环内增量、无压缩的常态）→ `added = new[len(old):]`，记 added 结束
2. **否则锚点对齐**：从尾部指纹（末条消息 hash）向前扩展，找 old 的最长后缀段在 new 中连续原样出现的位置 `anchor = old[i:] == new[j:j+len]`
   - `vanished = old[:i]`（被压缩/砍轮次/减半截断走掉的部分）
   - `inserted = new[:j]`（system + 摘要对等插入物）
   - `added = new[j+len(anchor):]`（本轮新增，含当前用户消息）
3. 分类落盘（对 vanished + added）：
   - user 消息且以「Our previous history conversation summary: 」开头 → 动作① 存摘要，不落原文
   - 固定 ACK assistant 句（「Acknowledged the summary of our previous conversation history.」）→ 跳过
   - role=system → 跳过
   - role=tool / assistant 带 tool_calls → 落原文但结果超 2000 字符截断占位（防文件膨胀）
   - 其余 user/assistant → 按 3.2 格式 append 当日 md
- 基准 = store 中该会话 `snapshot`；新会话/新周期首请求：只记录不追加
- 快速判定：`count + head_fp + tail_fp` 一致则直接判无变化，跳过全量比对
- 覆盖三种压缩形态：LLM 摘要压缩、砍轮次（TruncateByTurns）、压缩后仍超窗的减半截断（都是"前段消失"，锚点算法通吃）
- 压缩 LLM 失败时 AstrBot 返回原列表（本次不压缩），对 diff 透明

### 4.4 压缩结构验证（M1 已完成 ✅）

读源码 `core/agent/context/compressor.py` + `context/manager.py` + `runners/tool_loop_agent_runner.py`：
- 压缩器选择：custom > LLMSummaryCompressor（配 llm_compress_provider 时）> TruncateByTurnsCompressor（默认，砍最老轮次、无摘要）
- 摘要压缩产出结构：`_extract_system_messages(首部连续 system) + user 摘要消息 + 固定 ACK assistant + 最近轮次原文平铺`
- 最近轮次预算：`total_tokens × keep_recent_ratio(默认 0.15，钳制 0-0.3)`，按整轮保留，最新用户轮强制保留
- 压缩在每次 LLM 调用前执行（runner L804-816），结果写回 run_context.messages 持久化
- diff 分支已定：锚点对齐算法（4.3），无需再跑对话验证

## 5. worker 实现（`digest_worker.py`）

### 5.1 调度

- `initialize` 时启动 asyncio 任务 `_digest_loop`：计算距下一个 `digest_time` 的秒数 → sleep → run
- 重启补跑：启动时若 `last_run_ts` 早于上一个 digest 点且窗口内有新消息 → 立即补跑一次
- 窗口日志：每次 run 打「收集 起 → 止」，覆盖过渡日/补跑超窗溯源

### 5.2 单次 run 流程（锁外准备、锁内落盘）

1. 窗口 = watermark → now，推进前先留旧值（失败可重试）
2. 遍历 store 中 `summary_consumed=false` 或有新原文的会话：
   - 补尾：snapshot 中 `last_compress_ts → now` 的尾部消息，超 ~2000 token 才发一发补尾摘要（provider 直连，代码块占位+截断）；不足直接原文
   - 补尾原文 append 当日 md（`[tail:会话]` 区块）
3. 汇总日记输入 = 存储摘要 + 补尾摘要（+轻日子判定：纯原文且无摘要 → 默认不写日记，可配置）
4. 日记：人设 LLM 直连（person卡进 system，prompt「以角色风格把以下内容总结为日记」），死规矩提示词内置（只记决定/结论/坑/偏好，不抄代码，改动记文件名）
5. 成功 → append 日记区块；失败/空返回 → 摘要原文当记录落盘（`[摘要代记]` 标注）
6. 清 `summary_consumed`；raw_ttl_days>0 时清扫到期老文件（重写留日记删原文段）
7. 推进 watermark，落盘 store

### 5.3 LLM 直连

- 复用 `Embedder._get_provider` 模式取 provider，日记用人设绑定的 chat provider
- 人设文本来源：待确认（AstrBot 人设配置读取 or 插件内固定角色句，见 8.3）

### 5.4 watcher 增量阈值（防大文件反复全量重建）✅ M5 已实现

- 现状：`_on_md_changed` 对任何 .md 变化整文件 delete+reindex
- 问题：当日 md 一天高频追加（每条消息都可能触发），大文件反复全量 embed 成本高
- 方案：MemoryFiles/VectorDB 侧记每文件已索引字节偏移（存 `data/index_state.json`），变化量 < 阈值（默认 2000 token）不重建，超阈值才整文件重建；watcher 本身已有防抖
- 注入文件（MEMORY.md/SOUL.md）维持跳过索引

## 6. 注入块动态化（`_refresh_inject` → `_build_inject`）

每次请求现算（`_inject` 内），拼三段：

1. 现状指针块（digest 开启时）：
   `记忆文件：最新日记 memory/日期.md（覆盖 起→止）；原文已在该目录可直接读/grep，日记尚未生成`
2. 小本子指令块：`notebook_name` 模板 + 提问门槛（只问稳定事实，不问即时状态）
3. 现有 inject_text（MEMORY.md 内容）

- 仍用 `INJECT_MARKER` 包裹整体，避免重复拼接
- 代价备注：system prompt 每请求微变 → 模型侧 prompt cache 不命中，可接受
