# OpenClaw 记忆插件 工程报告 第四版（2026-08-17 03:25）

> 接续第三版（M6 收官）。本版聚焦 M7-7.1：原文落盘路径优化。

## 1. 问题定性

M6 代码功能正确，但原文落盘路径有两个体验问题：

| 问题 | 表现 | 根因 |
|---|---|---|
| 插件增加 LLM 首 token 延迟 | 每次 LLM 请求前，`_capture` 跑 diff（含 DP）才能放行 | hook 挂在 `on_llm_request`（关键路径），diff 在 LLM 调用前执行 |
| 一轮延迟 | 当前轮消息要等下一次 `on_llm_request` 才落盘 | `on_llm_request` 触发时当前 user 消息刚加入 context，但"落盘"发生在下一次请求的 diff 里 |

内容本身没问题：raw 文件全量存、走 grep、密度低无所谓。要优化的是**写入动作的时机和方式**。

## 2. 现有路径分析（要改的）

### 2.1 触发点

```python
@filter.on_llm_request()
async def _capture(self, event: AstrMessageEvent, req: ProviderRequest) -> None:
    session_id = req.session_id or str(event.unified_msg_origin)
    await self.differ.process(session_id, req.contexts or [])
```

- 每次 LLM 调用前触发（含 tool call 迭代）
- 一轮对话（user→bot tool call×3→bot final）会触发 4-5 次
- 全部在 LLM 请求发出**之前**执行完

### 2.2 写入逻辑（ContextDiffer.process）

```
process(session_id, contexts)
  ├── normalize(contexts) → msgs（全量标准化）
  ├── 与 store 中 snapshot 对比
  │     ├── count 相同 + head_fp + tail_fp 相同 → return（无变化）
  │     └── 不同 → _diff(old, new)
  │           ├── _anchor_align：尾部锚定 → 失败则 DP 兜底
  │           └── 返回 (vanished, inserted, added)
  ├── 合并三路 → 过滤 system/summary/ack → raw list
  ├── fps 去重（_load_seen_fps 读文件已有 fp 集合）
  └── 写入 raw 文件 + 更新 snapshot（_pack(msgs) 全量）
```

### 2.3 复杂度来源

| 组件 | 行数 | 用途 |
|---|---|---|
| `_anchor_align` | ~40 | 处理 context 压缩后的消息重排 |
| `_diff` + `_diff_dbg` | ~30 | 分三路找出增量 |
| `_pack` / snapshot 全量 | ~10 | 存完整消息列表用于下次对比 |
| fps 注释 + `_load_seen_fps` | ~20 | 文件级去重 |
| `process` 主流程 | ~50 | 胶水 |

总计 ~150 行在关键路径上跑。

## 3. 目标路径设计

### 3.1 触发点：`on_llm_response`

参考 meme_manager 用法：

```python
@filter.on_llm_response(priority=99999)
async def _capture(self, event: AstrMessageEvent, response: LLMResponse) -> None:
```

**为什么用这个：**
- LLM 已返回，不阻塞首 token
- 消息已确定（assistant 回复已生成），无"半完成"状态
- tool call 多次触发也无害：第一次写入后，后续 `len(full) <= count` 直接 return
- 语义贴切："LLM 回完了，该记账了"

### 3.2 数据来源：DB 读取

不走 `req.contexts`（请求体），改从 DB 拿全量：

```python
async def _fetch_full(self, session_id: str) -> list[dict]:
    db = self.context.get_db()
    rows = await db.get_conversations(
        user_id=session_to_db_user_id(session_id)
    )
    if not rows:
        return []
    row = max(rows, key=lambda r: r.updated_at)
    full = await db.get_conversation_by_id(row.conversation_id)
    if full is None:
        return []
    raw = full.content or "[]"
    if isinstance(raw, str):
        raw = json.loads(raw)
    return normalize(raw, think_cap=self.think_cap)
```

跟 `DigestWorker._fetch_tail` 同源（抽成共享函数或复用）。

### 3.3 写入逻辑

```python
async def _capture(self, event, response):
    session_id = ...
    entry = await self.store.get(session_id)
    count = int(entry.get("raw_count") or 0)

    full = await self._fetch_full(session_id)
    if len(full) <= count:
        return  # 无新消息

    # 压缩 fallback
    if len(full) < count:
        # context 被压缩了，用 fps 集合对比
        path = await self._bucket_path(session_id)
        seen = _load_seen_fps(path)
        fresh = [m for m in full if m["fp"] not in seen]
        count = len(full) - len(fresh)  # 重置 baseline
    else:
        fresh = full[count:]

    if not fresh:
        return

    # 过滤 + 渲染 + 去重 + 写入
    raw_msgs = [m for m in fresh if m["role"] != "system" and not _is_summary_ack(m)]
    if not raw_msgs:
        await self.store.update(session_id, raw_count=len(full))
        return

    path = await self._bucket_path(session_id)
    seen = _load_seen_fps(path)
    new_pairs = [(m["fp"], self._render(m)) for m in raw_msgs if m["fp"] not in seen]
    new_pairs = [(fp, s) for fp, s in new_pairs if s]
    if new_pairs:
        async with self.lock:
            block = f"## [{session_id[:24]}]\n"
            block += "\n".join(s for _, s in new_pairs) + "\n"
            block += FPS_PREFIX + " ".join(fp for fp, _ in new_pairs) + "-->\n"
            self.daily_file_for(session_id).append_to(path, block)

    await self.store.update(session_id, raw_count=len(full))
```

### 3.4 Store 字段变化

| 旧字段 | 新字段 | 说明 |
|---|---|---|
| `snapshot.count` | `raw_count` | 已写入 raw 的消息数（int） |
| `snapshot.head_fp` | — | 删除（不再需要） |
| `snapshot.tail_fp` | — | 删除（不再需要） |
| `snapshot.messages` | — | 删除（不再存全量列表） |
| — | `raw_last_fp` | 最后写入的 fp（可选，调试用） |

兼容：首次升级时如果 `raw_count` 不存在但 `snapshot.count` 存在，迁移取 `snapshot.count`。

## 8. 附带收益：天数归桶天然准确

**现状问题（DB 归桶）：**
- raw 文件由 digest worker（21:45）或 `on_llm_request` 的补尾机制写入
- 归桶靠 DB `updated_at`（已排除为"稳态不触发"，但本质仍是间接推断）
- bot 离线几天再回来：全量积压消息一次性塞进**一天**的文件，天数归属靠猜

**hook 路径下：**
- `on_llm_response` 实时触发，归桶日期 = `datetime.now().date()` = 对话发生那天
- 每天的消息天然写进那天的文件，不存在"几天塞一天"
- bot 离线三天再回来：day1.md / day2.md / day3.md 各自独立，都是当天实时写入的

**对 diary 补跑的影响：**
- worker 启动时检查：哪些日期有 raw 文件但没有 diary → 逐天读对应 raw → 逐天生成 diary
- 不用从 DB 捞全量再分桶——raw 文件本身就是按天分好的
- 每天的 diary 输入只有那天的内容，不会几天的对话一锅炖给 27b

**结论：** hook 实时写入从机制上消除了天数归桶问题，比任何"选对时间戳"的 patch 都彻底。

## 9. 摘要结构化 + 日记提炼优化（Issue 2）

### 9.1 问题

当前 diary 生成依赖 `summary_states`（多次压缩的滚动摘要列表）+ `_fetch_tail`（DB 补尾），链路长且依赖 DB。压缩摘要本身是全量改写的（每次压缩面目全非），diff 追踪意义不大。

### 9.2 方案：利用压缩提示词注入固定结构

**核心思路：不改存储，改格式。** 在 AstrBot 压缩上下文时使用的系统提示词里注入固定结构标记，让 LLM 生成的摘要自带"经验段"。

**注入的压缩提示词结构（示意）：**

```
...（AstrBot 原有压缩指令）...

摘要格式要求：
1. 先用 2-3 句概述对话背景和氛围（定调性用）
2. 然后列出关键经验，格式如下：
[经验 START]
- （决定/结论/踩坑/偏好，每条一行）
[经验 END]
3. 如果没有明确经验，经验段写"无"
```

**效果：压缩摘要天然分段**
```
今天整体是轻松的技术讨论氛围，聊了 AstrBot 插件开发和晚饭吃什么...

[经验 START]
- 决定了 on_llm_response 做落盘 hook
- 踩了 sys.modules 缓存的坑
- 冰城吃火锅不加醋
[经验 END]
```

### 9.3 日记生成（21:45）

**输入：**
- 最新压缩摘要（含经验段 + 背景段）—— 如果当天有压缩
- 当天 raw 文件尾部（最近几轮没被压缩到的对话）—— 兜底
- 如果当天没触发压缩（对话短），直接用 raw 全文

**diary 系统提示词关键约束：**
```
以下是今天的对话摘要和尾部原文。写日记时：
- [经验 START] 和 [经验 END] 之间的内容**必须保留**在日记中（可改写但不可省略）
- 摘要其余部分和尾部原文是背景基调，参考其语气和情感，不必逐条覆盖
- 300-800 字，第一人称日记体
```

**为什么这样好：**
- 经验段是"骨架"：保证不丢关键决定/结论
- 背景段 + raw 尾部是"血肉"：给人情味、情绪、调性
- 纯聊天用户：经验段可能是"无"，但 raw 里有"今天好累""看了个番"，diary 照样有温度
- 写代码用户：经验段密集，diary 重点突出
- 不需要 diff：摘要本身就是最新全量，直接用
- 不需要额外文件：结构在摘要内部，不产生新存储

### 9.4 与 Issue 1（hook 落盘）的关系

| 层 | 内容 | 写入时机 | 用途 |
|---|---|---|---|
| raw md（Issue 1） | 全量对话原文 | `on_llm_response` 实时 | grep 检索、完整记录 |
| 压缩摘要（Issue 2） | AstrBot 生成的结构化摘要 | AstrBot 压缩时自动生成 | diary 提炼的输入 |
| diary | 最终日记 | 21:45 worker | 向量索引、长期记忆 |

三层各司其职，不重复、不冲突。

### 9.5 前置依赖
